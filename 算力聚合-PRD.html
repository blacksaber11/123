本版（v1.2）相对 v1.1 的变更

v1.1 确立了「线上只做信息与线索撮合，签约、付款、交付全部在线下完成」的轻模式。本版在此之上再收窄一层，并补齐商品信息深度：

  1. 商品信息更全面——新增「成色」（全新 / 二手 / 拆机件 / 翻新）、「税费」（含税 / 不含税 / 可开专票 / 可开普票）、「供给类型」（现货 / 期货）三组必填属性，定价支持多档位（起订量档、长期租期折扣）与押金、账期声明；搜索筛选同步新增这三个维度。
  2. 咨询前先填意向——浏览不要求任何信息；点「咨询」后必须先经过一页「咨询信息填写页」，需求项必填、材料项选填，确认后才生成线索。材料填了就打标签，不填也能提交。
  3. 意向对照——平台把买方意向与货主商品在 9 个维度上并排展示，供客服逐维核对。只做字段并列与差值标注，不做结论判断。
  4. 对接全部转到微信——取消 v1.1 的「客服居中释放联系方式」，改为客服拉三方企业微信群（坐席 + 货主联系人 + 买方联系人）。建群即释放、即商品转洽谈中、即线索转已对接。平台只提供信息发布与对接前置流程，不承载任何交易动作。
本版（v1.3）相对 v1.2 的关键收敛

v1.2 把对接收窄到三方企微群，但线上链路仍延伸到合同登记、服务费核销与开票。本版把线上终点一次性定死在「建三方企微群 + 引导线下对接」，其余全部收进管理端内部，并补齐买方决策与客服接单所缺的两块信息：

  1. 商品详情页补两块内容——买方点开商品后，必须能逐项看到关键信息是否已上传（所有权证明、设备图片、规格文档、第三方报告、同台核验、先验后付、短周期试用、接单要求），以及固定五步的商品交易流程说明。完整度只给「已上传 N 项 / 共 8 项」的计数，不给评分、不给结论。
  2. 咨询即分发——买方提交咨询的那一刻，线索同时分发到三处：客服工作台（带提醒）、货主端（站内消息 + 企微 + 短信兜底）、买方回执。货主看到的是买方标签摘要（强主体 / 可验资 / 材料齐全 / 已实名），买方看到的是「信息完整度会影响货主是否愿意继续接受咨询」的前置提示。
  3. 管理端咨询详情页——客服点开一条咨询，同屏看到三块：上传该商品的货主与商品信息、该咨询的买方信息（联系方式必须展示）、双方的9 维意向对照。详情页是建群、标记可交易、关闭线索的唯一操作入口。
  4. 合同与收费内部化——线下对接之后的事归管理端客服与财务：成交登记、服务费台账、开票记录全部只在管理端内部使用（用于核算与提成），买方与货主侧没有任何账单、收款页、发票入口。
本版（v1.4）相对 v1.3 的两处扩展

v1.3 把链路定死在「建群 + 引导线下」，链路只有「买方看货 → 咨询」一个方向。本版补上反方向，并把工程可行性一次性说清：

  1. 买方可以反向发需求（求购单）——买方发布求购单时必须选择「是否上传验资视频」「是否支持同台验收」，勾选后在需求卡片上显示对应标签，货主在需求大厅可见；同时填写预算、所需型号、台数。货主看到后必须绑定自己在售的一条商品发起响应，生成「求购响应」类别的线索，与「商品咨询」线索进入完全同一套撮合流程（状态机、分配、SLA、建群、登记、台账一致），管理端工作台只按「来源类别」分 Tab，不是两套流程。
  2. 新增第八章「技术可行性与非功能底线」——回答流程流转可靠性、信息隔离加密、技术栈选型、大批量商品管理、多人在线降压、Redis 四级缓存分级、服务器与账号防护、加密访问可行性，并给出 10 条「不达标不上线」的验收清单与容量/性能基线。本章不改产品行为，只约束实现。

同时买方资质摘要由四项扩为六项（新增「已提供验资视频」「接受同台验收」），两条链路口径一致。本版一次性拍板 07 章的全部取值，不再保留待确认项。

本版（v1.5）相对 v1.4 的结构性调整

v1.4 之前，平台是「买卖双向发布 + 线索三端分发」。本版把用户端收敛为类闲鱼的信息流形态，并把所有咨询收口到平台，货主端降级为只读的计数与资质展示：

  1. 发布类型三分——发布入口先二选一定「出售」还是「求购」，出售下再选「整机售卖」或「租赁」。出售与出租共用同一套商品模型，用「交易方式」字段区分；求购需求沿用 v1.4 的求购模型。用户端首页因此分为「在售货源」与「求购需求」两个 Tab，不做混排。
  2. 用户端只看到货，联系不到人——商品卡片与详情页展示价格、数量、城市、发布时间、咨询人数与货主资质标签，不展示任何联系方式、不接受站内私信。买方要接触货主，唯一入口是「发起咨询」，且必须先填完咨询信息页才能提交。
  3. 咨询只进平台管理端——线索创建后不推送到货主端。货主只在自己的商品下看到「本商品已有 N 人在咨询」的计数，以及该商品下咨询人的六维资质标签分布，看不到咨询人的身份、需求摘要与联系方式。由坐席用微信主动联系双方，货主没有绕过平台联系买方的通道。
  4. 咨询热度与咨询人筛选规则——每个商品维护一个精确去重的咨询人数（同一买方对同一商品只计 1 次），买卖双方都能看到这个数字但不看到人。管理端新增咨询人筛选规则引擎，支持按全局 / 品类 / 单商品配置条件，命中后输出三档结论：P0 拦截（不进坐席队列）、P1 待核（标黄提示）、P2 优先（置顶并标记「优先推荐」），用于把明显不真实的咨询挡在队列外、把资质齐全的买方顶到最前。
  5. 逐单资质核对单——每一条线索配一张核对单，逐项记录「要求内容 / 买方提供状态 / 验证方式 / 核验结果 / 核验人 / 时间」。平台只记录「核对了什么、怎么核的」，不写「真实 / 有效」的结论；标记为必验的项未完成核验前，不允许建三方企微群。
  6. 货主侧询单动作降级——取消货主端「可交易 / 不可交易」的站内按钮，改为坐席微信触达后由坐席在管理端回填；货主侧仅保留商品管理（上下架、改价、标记已成交）与咨询计数查看。
  7. 双向筛选，两套独立筛选器——买方在「在售货源」按交易方式 / 成色 / 税费 / 供给类型等筛商品；卖方在「求购需求」（卖家市场）按型号 / 数量 / 预算 / 周期 / 城市 / 税费 / 成色 / 验收要求 / 需求状态筛需求，条件互不影响。卖方筛完在需求详情页「发起咨询」，必须绑定自己的一条在售商品，线索来源记为求购响应，同样只进管理端。

本版不新增功能编号：筛选规则引擎与逐单资质核对单作为 F6 的小节，咨询人管理与拦截箱作为 F11 工作台的新增视图。五条产品红线、线上终点（建群 + 引导线下）、1% 服务费口径均不变。

01背景与目标

从观察到的问题，推导出本产品唯一要做的三件事。

1.1 观察到的问题

算力（GPU 服务器 / 整机 / 卡时）是大额、非标、无法远程验证的资产。现有交易路径在三个环节同时断裂：

  • 供给端：持卡方与机房有闲置资源，但没有稳定客源，只能靠朋友圈、行业群发布，信息一次触达即失效，且天然不愿意公开自己有多少卡、在哪。
  • 需求端：采购方看不到货源，也无法判断对方是否真的持有设备。看到一个报价，无法分辨是持卡方、代理商还是中间商转手。
  • 交易端：金额大、设备无法远程验收，最终必然回到线下——大额非标交易不可能靠线上表单完成，真正卡住双方的是找到对的人并建立可信接触，而不是缺一个下单按钮。
  • 匹配端：一旦把双方的联系方式直接放开，最先涌来的是大量中间商询价、无效询盘与同行探价，真实买方被淹没。平台要做的不是把联系方式给出去，而是先把咨询收口、按规则筛一遍，再把合适的人接上。

1.2 产品决策

平台不做交易，只做居间。货款始终由买方直接付给货主，平台不经手、不冻结、不担保；平台只收取成交金额 1% 的居间服务费。

据此，平台向双方交付的是三件事，而不是"一个交易市场"：

  1. 可核对的信息——结构化的设备规格、成色（全新 / 二手）、税费（含税 / 不含税）、供给类型（现货 / 期货）、多档位报价与交易说明；商品详情页另行列出关键信息是否已上传的逐项清单与完整度计数，以及固定的五步交易流程说明。买方能按型号、价格、成色、税费、供给类型、城市筛出真正匹配的货源，并在点开商品时就知道这条货源的信息齐不齐。
  2. 可触达的线索——每一条咨询先转成一份结构化意向（需求必填、材料选填），提交后只进平台管理端，不进任何用户端。买方的需求摘要与联系方式只在管理端可见；货主只能看到「本商品已有 N 人在咨询」与该商品咨询人的资质标签分布（汇总计数，无名单）。咨询先过一层筛选规则（拦截 / 待核 / 优先），客服再做逐单资质核对，确认后建三方企微群把双方接上。线上到此为止，后续全部在线下发生，平台只登记结果。
  3. 可核算的居间费——成交后由客服在管理端内部登记成交金额与服务费，财务线下收款、内部核销。买方与货主侧不出现账单、收款页与发票入口，这份台账只用于平台内部核算与提成。

1.3 期望的可观测结果

  • 买方进入首页即可在「在售货源」与「求购需求」两个 Tab之间切换，直接看到所有货与所有需求的价格、数量、城市、发布时间与咨询人数；不必先注册资料、也不必先联系谁。
  • 买方可以按型号搜索、按价格排序、按条件筛选，在几秒内从大量在售货源里缩小到可谈的候选；且能按成色、税费、现货期货这些过去只能靠私聊问清的硬条件直接筛。
  • 每一笔咨询都先转成一份结构化意向，客服不必在对话里反复问同样的问题；意向与商品在一屏内并排对照，条件对不对得上一眼可见。
  • 买方点开任一商品，都能直接看到关键信息是否已上传与完整的五步交易流程，不必逐个私聊问「你有没有所有权证明」。
  • 每一笔咨询都沉淀为一条有状态、有责任人、有下一步动作的线索，只落在管理端；每次撮合都对应一条可审计的建群记录。货主在任何页面都无法取得咨询人身份与联系方式。
  • 每个商品都有精确去重的咨询人数，买卖双方看到的是同一个数字；咨询热度成为判断「这条货是不是真有人要」的公开信号，但不暴露任何一个咨询人。
  • 咨询进入坐席队列前先过一层可配置的筛选规则：明显不真实的咨询被拦在队列外，资质齐全的买方被顶到最前并标记「优先推荐」，坐席的 5 分钟首响落在最值得跟的线索上。
  • 每一条进入跟进的线索都有一张逐单资质核对单，写清「要求什么、提供了什么、怎么核的、谁核的」，必验项未完成不能建群；平台只记录动作，不下真伪结论。
  • 客服点开一条咨询，就能在同屏看到货主、商品、买方与联系方式，不必另外翻资料；坐席从接单到建群的平均处理时长可被度量。
  • 线上流程以「建群 + 引导线下对接」为终点，之后由双方自行完成；平台内部对每笔成交留一条成交内部登记与服务费台账记录，用于核算与提成。
  • 商品状态反映真实在售情况：卖掉了就下架或标记已成交，不制造虚假在售。
  • 平台在任何纠纷中都能证明自己只提供了信息服务，且已履行居间义务。
定价成立的前提

买家愿意为 1% 付费，不是因为平台担保交易，而是因为"货找得到、人找得到、费用算得清"。因此线上唯一不可让渡的价值是把对的人和对的货源接上并留下痕迹；线下由双方自行完成，平台不做见证也不收见证费。

02范围

03产品模型

先定义角色、对象与不可越界的约束，再定义功能。所有功能需求章节都以此为准。

3.1 单一账号，双身份

平台只有一个用户体系，不区分"买家 App"和"卖家 App"。同一账号可在货主身份与买方身份之间切换：发布出售 / 出租时进入货主侧（拥有商品即出现「货主工作台」），发布求购或对商品发起咨询时进入买方侧（「我的咨询」与「我的求购」）。发布入口先二选一，选定后决定这次发布落在哪一侧。

同一实名主体同时作为买方与货主参与同一笔交易时，系统在撮合环节拦截并标记为自成交，该笔线索不计入成交记录、不产生服务费。

无论处于哪一侧，用户之间都不能直接建立联系：页面上没有联系方式、没有私信入口、没有「联系卖家」按钮；唯一出口是「发起咨询」，由平台坐席接管后续对接。

命名即定位

产品里不存在"订单"这个概念，只有"咨询线索"。这不是文字游戏：它让平台在语言与系统上都站在服务提供方而非交易方的位置，也避免出现"下单—支付"这类会被理解为平台履约的交互。

3.3 五条产品红线

以下五条是所有功能的前置约束。任何新功能与红线冲突时，功能让步。

红线具体含义在产品上的体现
一、不归集资金不代收、不冻结、不设资金池、不做分账无支付下单流程；货款由买方直接付给货主；平台只收服务费，由承担方（默认买方，可约定货主承担或双方按比例分担）线下打款到对公账户，财务只在管理端内部台账登记；不向买方与货主出具任何账单、收款页或发票申请入口
二、不担保履约不承诺设备存在、规格真实、按时交付、可退款无"保真""兜底""先行赔付"话术；无下单、无担保交易、无平台见证环节；违约责任由买卖双方在自行签署的合同中约定
三、不背书材料真伪仅登记提交状态，不做真伪核验标签只写"已上传"；统一免责角标不可折叠；平台不检查、不抄录、不运行设备
四、不公开双方信息双方信息不公示、不批量可见，只在撮合成立时由客服建三方企微群，在群内释放给交易对手联系方式不进入任何列表页与搜索结果；建群是逐条线索的人工动作并全量留痕；群成员固定三方，不引入第四方
五、居间主体统一为公司签约主体 = 收款主体 = 开票主体禁止个人名义收取服务费；服务费只进对公账户

红线四的产品化延伸：信息释放由一个群承载，由一个人开户

在轻模式下，平台不再有"合同生效即自动披露"这样的系统事件，信息释放落回客服。唯一的释放动作是建一个三方企微群——建群即释放，没有第二种途径。因此必须用机制保证这个动作不会失控。新功能上线前用三个问题自查：

  1. 谁建的群？必须是平台企业微信坐席，且是该线索的负责坐席，逐条线索人工触发。没有责任人的自动建群一律不允许，客服也不得把建群权限转授给货主或买方。
  2. 建群之后，双方在这个群里看到什么？只有「公司名 + 联系人 + 电话/微信 + 资质标签摘要（不含材料原件）」，加上建群时自动推送的意向对照摘要。看不到对方提交过的任何材料原件，也看不到对方在平台内的其他信息。
  3. 如果这次建群后来被证明是错的，能不能查清楚是谁、何时、把哪两方拉进了哪个群？不能，就不允许上线。
  4. 在信息释放之前，该核的资质核完了没有？核对单里的必验项必须全部完成才能建群，核验人与时间可追溯；核对单只记录动作，不产生真伪结论。
  5. 货主在此之前，有没有从任何页面拿到咨询人的身份与联系方式？不能有。货主侧只显示去重咨询人数与资质标签。
群是信息释放的容器，不是交易场所

群内的一切沟通都发生在平台之外，平台不解析、不转录、不据此裁决。平台在群里只做流程协调与信息对齐：推对照摘要、催回填节点、记录结果。任何"群内达成的约定"都必须回到站内被登记，否则不算数。

04功能需求

每个模块按"目的 → 触发 → 规则 → 结果与状态变化 → 字段 / 异常"展开。跨模块复用的规则集中在第五章。

F1 账号与实名

目的：让双方在进入交易前具备可追溯的真实身份，同时不因注册门槛流失浏览型用户。

触发：用户注册；或未实名用户在受限动作处被引导。

规则：

  • 注册即可浏览、搜索、筛选、查看商品详情与货主公开信息，不要求实名、不要求填写任何资料。未登录用户也可浏览，仅在点击「咨询」时要求登录。
  • 以下动作要求实名：发起咨询（进入咨询信息填写页时校验）、上架商品、发布求购需求；P1 起「申请验资」（平台对接验资机构）也要求实名。未实名用户点击「咨询」时，先完成实名，再回到信息填写页，已填内容不丢失。
  • P0 期买方不通过平台验资，只能自行上传第三方出具的《验资报告》《审计报告》等材料，对应标签为 L2「已提供」。
  • 个人实名：人脸核身 + 身份证 OCR。企业实名：工商信息比对 + 法定代表人认证；经办人办理时须上传授权书。
  • 实名信息一经认证不可自行修改；信息变更走人工复核。

  • 完整度不进入排序权重（排序分见 F5），避免诱导货主为排序而堆材料。

交易说明的设定规则

  • 货主自定义交付与验收描述，但至少必须填写真实可核的规格描述与验收标准。
  • 验收标准由货主填写，是买方判断能否接受的直接依据，不要求平台判断其合理性。
  • 付款方式仅作声明（银行转账 / 现金 / 其他），平台不据此提供支付能力。
  • 商品上架后修改交易说明，只影响之后产生的线索；已生成的线索保留咨询当时的商品快照，快照不可被后续修改覆盖。
  • 「是否支持买方同台核验」是货主对买方的单方承诺，平台只做登记与展示，不做安排。
  • 接单要求是货主对买方的期待（如需验资、需某数量以上），用于意向对照时双方核对；它不构成平台对买方的强制条件，也不进入平台的审核流程。

状态流转规则

  1. 咨询不改变商品状态。买方发起咨询后商品仍为「在售」，线索进入「待分配」。
  2. 客服完成条件核对、联系货主并取得"可交易"确认后，执行建三方企微群；建群的同时商品置为「洽谈中」，线索进入「已对接」，双方在公司名、联系人、电话/企微名片与标签摘要层面互相可见。三者是同一个动作的三个结果，不允许分步执行。
  3. 洽谈中不隐藏商品。商品继续展示在列表与详情页，只是咨询入口不可用；这既让买方看到货源真实存在，也避免"货凭空消失"的观感。P1 起追加「登记候补」入口。
  4. 同一商品同一时刻只允许一条线索处于「已对接」。并发时后进入者被阻塞并提示客服介入。
  5. 标记已成交必须关联线索并填写成交金额。该金额是线索侧的成交预估基数，最终计费以成交内部登记金额为准（见 F9）。标记后商品转「已成交」，线索同步转「已成交」。
  6. 洽谈中超过 7 天[基准值] 未推进，系统仅提醒货主与坐席，不自动回滚——商品是否继续对外由货主自己决定。
  7. 已成交不可改回在售。若货主仍有剩余资源，使用「复制为新商品」重新走审核流程。
  8. 线索关闭时，若商品处于「洽谈中」且成交未发生，商品恢复「在售」；货主已主动下架的，保持「已下架」。

谁可以下架 / 标记已成交：货主可对自己的商品执行下架，以及在「洽谈中」时标记已成交（须关联该商品唯一处于「已对接」的线索并填写成交金额）；客服可在自己负责的线索范围内代为下架、代为标记已成交，主管可操作全平台商品；审核员不参与。

异常：咨询点击瞬间商品已被另一条线索置为「洽谈中」 → 不创建新线索，提示「该货源洽谈中，可换货源或发布求购需求」；货主在洽谈中下架 → 视为放弃本单，线索转「已关闭」、企微群转「已归档」、商品转「已下架」，通知买方并推荐同类货源，记录货主行为。

F4 标签体系

目的：让"提交过材料"这件事被看见，从而形成"上传有益、不上传也无惩罚"的正向激励，同时避免任何背书印象。

同一个热门商品一天可能来几十条咨询，其中大量是比价、试探、中间商转手、甚至同行骚扰。平台不在用户侧做筛选器，而是在管理端用一套可配置的规则先把线索分档，再决定谁先被对接。规则只输出档位与命中原因，不输出"这个人是真的 / 是假的"这类结论。

筛选规则只做排序，不做验证。真正决定能不能把这一单推到货主面前的，是坐席在每一单上逐项完成的资质核对。核对单是线索上的一个必填区块，必验项未全部完成，不允许建群。

状态机

已拦截规则判 P0，不进队列→ 待分配→ 跟进中→ 已对接→ 已成交

新线索创建后先按筛选规则判档：P0 直接进「已拦截」，不进「待分配」，仅客服组长可在 24 小时内复核恢复为「待分配」；P1 / P2 / 默认进「待分配」。除「已成交」以外的状态均可转「已关闭」，关闭须选择结构化原因并留痕；「已成交」只有在成交内部登记作废且应收清零时才允许关闭（见 5.2）。允许的回退只有一条：「跟进中」→「待分配」（货主 48 小时未响应询单或货主婉拒时）。「已对接」不允许回退——一旦建群，线索只能向前到「已成交」或关闭，避免同一线索被重复撮合、也避免同一个群对应两种状态。其余状态只能向前推进或关闭。

三方企微群规则

三方群是本模式唯一的"对接发生地"。平台不拉群，就没有任何把双方接上的手段；平台坐席进了群，就要面对群内内容带来的责任问题。因此群的边界必须写死。

规则项要求
建群人必须是平台企业微信的坐席账号，且是该线索的负责坐席；其他角色不能建群
群成员固定三方：负责坐席 + 货主联系人 + 买方联系人。货主与买方各自只能代表自己一方，不引入第三方
建群前提① 线索处于「跟进中」；② 逐单资质核对单的全部必验项已完成；③ 货主已确认可交易，且「确认可交易」节点已在线索中回填；④ 双方联系人均已在企业微信上被坐席添加；⑤ 双方均已同意加入群聊。
重建群另走一条路径：线索为「已对接」、原群为「已归档」、经客服主管确认，可重建并生成新群标识
群内首条消息自动推送意向对照摘要，让双方一进群就看到同一份事实，避免各说各话
平台在群里的角色只做流程协调与信息对齐：居中澄清需求、提示差异、记录关键节点。不做议价中间人，不替任何一方报价，不对设备作任何判断
建群即释放信息建群动作同时释放双方的「公司名 + 联系人 + 企微/手机号 + 资质摘要（买方）/ 货主标签摘要（不含材料原件）」；本动作的留痕要求见 5.5
群内沟通内容平台不解析、不转录、不作为证据；只保留建群事实与双方回填的关键节点（确认可交易、确认成交、确认金额）
会话存档若开启企微会话存档，须在首次沟通时告知并取得双方同意；未取得同意的群不建立
群的生命周期线索关闭或标记已成交后，坐席在站内归档该群并标注结果；平台不强制解散群，但不再推送任何站内消息到该群
建群是红线四下唯一的越界动作

建群把双方从"隔离"变成"同处一群"，是平台信息边界的唯一破口。因此它必须满足四个条件：人工触发（无自动建群）、逐条可审计（记录操作人、时间、双方成员、群标识）、有前置条件（逐单资质核对单必验项全部完成 + 货主已确认可交易 + 双方已同意）、事后可追溯（核对单与节点回填随线索终身保留）。不允许"先建群后确认"，也不允许批量建群或由页面自动带出建群入口。

沟通在站外，结果在站内

群里怎么谈，平台不管；但成交必须回到站内被标记，否则服务费无从核销、标签无从累计、纠纷无从举证。这一条是"平台只做信息发布、不做交易"的落地底线。

关键节点回填

群内沟通与线下对接都发生在平台之外，平台无法自动获知结果，因此约定四个必须回填的节点：前两个在建群之前（它们都是建群前提），后两个在建群之后。四个节点都只用于平台内部推进与核算，不向买方与货主展示。

F7 成交内部登记（仅管理端）

目的：线下对接完成后，把成交事实以最小字段登记进管理端，作为内部服务费台账与提成的唯一依据，同时明确平台在双方合同中的角色是记录者而非签约方。

只对内有，对外无

本功能没有用户端入口：买方与货主在 App / Web 上看不到成交登记、看不到金额、看不到任何与本次对接相关的记录。它是客服与财务之间的内部动作，记录的是"平台自己知道这一单成了"，而不是"平台向双方确认这一单成了"。因此它既不产生任何通知，也不产生任何待办给用户。

触发：线索被标记为「已成交」时，系统自动创建一条状态为「待登记」的成交内部登记与一条「待登记」的服务费台账记录；由坐席补全信息并提交。客服也可在咨询详情页（见 F11）手动补登。

前置规则：

  • 平台不提供任何线上签署能力，不生成待签署的合同草稿，不发起签署流程；合同由双方在第三方电子签平台或线下纸质签署。
  • 登记的是成交结果要素（谁、何时、多少钱、怎么结算），不登记合同全文、不代理保管原件；双方自愿提供的留档材料可作附件，仅内部留存。
  • 登记必须关联一条已成交线索，无关联线索不允许登记，杜绝"无来源的成交"。
  • 只有客服坐席与客服主管可登记；财务只读并负责到账登记；审核员、只读观察者不可登记。
  • 登记人（坐席）对登记信息的真实性负责；登记后不可直接修改，只能作废后重新登记，原记录保留。
  • 登记金额与线索回填的成交金额不一致时，按成交内部登记金额计费，同时强制标记差异并转客服主管复核（见 F9）。

企业微信接入约束

  1. 只用企业微信，不用个人微信，客户资产留在企业侧，人员离职可交接。
  2. 会话内容存档默认不开启（见 07）：仅在争议线索中经双方书面同意后开启。开启时须在首次沟通时告知并取得同意，未取得同意的群不建立；不开启时，群内沟通完全不可追溯，平台只保留建群记录与关键节点回填记录。
  3. 企微中发出的每条平台侧业务消息必须携带站内回流链接，用户点击直接落到对应线索。
  4. 建三方群是对接发生的前提：坐席先分别添加货主联系人与买方联系人的企业微信，确认双方均同意后，由坐席建立群名为「线索编号 · 型号 · 城市」的三方群。群成员固定为坐席 + 货主联系人 + 买方联系人，不引入第四方，也不允许双方私下另建群替代（另建的群不受平台记录保护）。

坐席机制

5.2 状态机汇总

  • 商品：草稿 → 待审核 → 在售 ⇄ 洽谈中 → 已成交；洽谈中 → 在售（未成交退出，含线索关闭、群归档）；在售 / 洽谈中 → 已下架 → 在售；待审核 → 已驳回 → 待审核；待审核 → 草稿（撤回）。
  • 咨询线索：创建 → 先判档（P0 进「已拦截」，其余进「待分配」）→ 跟进中 → 已对接 → 已成交；待分配 / 跟进中 / 已对接 → 已关闭。「已拦截」只有两条出路：主管在 24 小时复核窗口内恢复投递（进「待分配」），或超窗口后 30 天自动清理；不适用常规「关闭」动作。进入「已对接」的唯一判定条件是三方企微群已建立，且建群前逐单资质核对单必验项已全部完成；「已对接」是线上服务的完成态，不可回退；「已成交 → 已关闭」仅在成交内部登记作废且应收清零时允许。
  • 意向信息快照：已提交（不流转、不可改）；更正以追加附注形式记录。
  • 企微群：已建立 → 已归档；已归档 → 已建立（重建，生成新群标识并新增一条建群留痕，原记录保留）。建群与线索转「已对接」、商品转「洽谈中」是同一动作。
  • 询单：待响应 → 已答复（可交易 / 不可交易）；待响应 → 超时未响应。询单只存在于管理端：坐席经企业微信 1v1 触达货主取得口头结论后回填，货主端没有对应入口、没有按钮、也没有这个状态。
  • 成交内部登记：待登记 → 已登记；待登记 / 已登记 → 已作废。无用户侧入口，用户不可见。
  • 求购需求：开放 → 洽谈中（至少一条响应线索进入「已对接」）→ 已成交；洽谈中 → 开放（无其他已对接线索）；开放 / 洽谈中 → 已关闭（买方撤销或到期）。关闭时同步关闭未对接的响应线索。响应方同样先过咨询人筛选规则，被 P0 拦截的响应只进已拦截箱、不进入响应计数与线索池。
  • 标签：生效 → 已陈旧 / 已过期；降级后重新上传材料可恢复生效。
  • 服务费台账：待登记 → 已登记（应收）→ 已到账（已核销）→ 已开票；已登记 → 已作废（成交内部登记作废）；已到账 → 已退款（线下退款后在台账标注）。台账只存在于管理端，无账单页、无支付入口。
  • 内部开票记录：待开票 → 已开具；已开具 → 已红冲（成交内部登记作废时）。由财务在台账内登记结果，不向用户开放申请与下载。

5.3 计算与取整

  • 服务费 = 成交内部登记金额 × 1%，四舍五入到元；低于最低服务费时按最低服务费收取。
  • 计价基数以成交内部登记金额为准。线索中标记的成交金额仅为预估，不作为计费依据；两者不一致时按登记金额计费并转主管复核。该计算全程只在管理端发生，不向买方与货主展示任何金额或结果。
  • 双方分担时，按登记时填写的比例拆分为两笔应收，各自计费与核销。
  • 折合单卡单日价 = 原始单价 ÷ 卡数 ÷ 单位天数（卡时按 24 小时、机日按 1 天、机月按 30 天、整包按最短租期折算），保留两位小数，仅用于排序与筛选。
  • 商品设有多档位价格时，折合单卡单日价取最低可成交档位计算；列表与排序处必须显示「起」字，详情页完整展示全部档位（起订量、租期、对应单价），不得只展示最低价而不说明适用条件。
  • 综合分 = 型号匹配度 30 + 价格分 25 + 标签分 15 + 城市匹配 10 + 活跃度 10 + 成交热度 10，满分 100。咨询人数与资质标签分布不进入综合分：咨询人数是商品侧的过程指标，进入权重会让"被问得多"变成"排在前面"，形成自我强化的马太效应；资质标签只用于管理端排序与核对，不在用户端参与排序。

08技术可行性与非功能底线

本章不定义接口、不排期，只回答两个问题：现有规则在工程上能不能稳定落地；哪些技术底线不达标就不允许上线。

8.1 结论

按本 PRD 的规则，P0 在技术上没有不可逾越的难点：没有支付、没有资金流、没有实时竞价，核心是"信息发布 + 线索流转 + 消息必达 + 信息隔离"。真正的压力不在服务器，而在客服处理能力——商品量可以横向扩，坐席人手不能。

但有五件事必须由系统保证，不能靠人工兜底：

必须自动化的规则工程手段靠人工的后果
同一商品同一时刻只允许一条「已对接」数据库唯一约束 + 条件更新（CAS），不是先查后写并发下两个坐席同时建群，双方被拉进两个群，商品状态错乱
联系方式只在建群后按线索释放字段级加密 + 接口层投影 + 角色鉴权，默认不返回一次接口疏漏就是整站手机号泄露，直接触碰红线四与个保法
消息必达（管理端坐席 / 货主侧汇总 / 发起方回执）Outbox 表 + 队列重投 + 死信 + 日终对账"咨询丢了"无法复现、无法举证，线索凭空消失
咨询人筛选判档幂等（同一线索只判一次）判档在同一事务内按规则版本计算并落库，重放不改变档位；规则读快照不读最新同一线索两次判档结果不同，货主侧咨询热度跳动、复核口径打架
状态推进留痕、不可裸改状态机白名单 + 条件更新 + 审计日志状态可以随手改，成交与台账的口径全部失效

8.3 信息隔离与加密（红线四的技术落点）

红线四要求"双方信息只在建群时释放"。这条规则在产品上表现为"不展示"，在工程上必须表现为拿不到：

层做法这条层挡住什么
传输全站 HTTPS（TLS 1.2+，优先 1.3），HSTS，禁止 HTTP 回退；管理端独立域名链路抓包与降级劫持
存储联系方式、证件号等独立表 + 字段级加密（AES-256-GCM），密钥在 KMS，业务表只存密文与盲索引拖库后直接拿到明文
检索手机号等精确查询走 HMAC 盲索引列，不做明文索引"按手机号搜人"变成批量导出工具
接口返回体用白名单 DTO，不在列表、搜索、求购需求列表任何接口返回对方身份与联系方式；默认不返回，需要时才按角色与线索授权单独取前端隐藏了、接口还在返回
展示按角色矩阵（5.1）渲染；坐席查看明文需二次验证，复制与拨打留痕；审核员、财务、只读观察者一律不可见内部人员批量抄号
材料对象存储私有桶，无公网直链；签名 URL 有效期 ≤5 分钟、绑定线索与查看人；视频单独加密桶，平台不播放、不转码公开材料 URL 被转发、被搜索引擎收录
日志应用日志、埋点、异常上报统一脱敏（手机号、证件号、地址）；导出需审批并加水印日志与监控成为泄露源
  • 求购需求只返回投影，不返回实体：求购需求列表的接口只输出需求摘要与六项资质摘要，买方主体只给"已实名企业"标识，不返回买方 ID 对应的公司名、联系人与任何材料信息。
  • 越权防护按"线索"授权：坐席只能读自己负责线索的明文联系方式；主管全量；其他角色即使拿到线索 ID 也只返回脱敏值。
  • 防枚举：所有对外 ID 用雪花或 UUID，禁用自增 ID；列表接口强制分页，禁止 id 遍历。
  • 测试与外包环境：只能使用脱敏数据，禁止把生产库副本导入开发环境。

8.5 大批量商品管理

P0 的量级假设：在售 + 历史商品 1 万～5 万条，日增 500 条，列表与筛选读峰值 2000 QPS，写峰值 50 QPS。这个量级不需要分库分表，但需要把"读"从主库挪走：

  • 表结构：商品主表保持窄表（ID、货主、状态、型号、城市、折合价、更新时间），规格明细放扩展表或 JSON 列；状态、货主、型号、城市、折合价建组合索引。
  • 列表与筛选走检索层：多条件筛选 + 排序 + 聚合计数交给 ES；MySQL 只承担详情回源与写。禁止在主库上做 count(*) 全量统计。
  • 深分页：列表上限 100 页，超出改用游标（search_after）；不做 LIMIT 100000, 20 这类查询。
  • 审核异步：提交即入队，审核员批量操作（一次最多 200 条通过 / 驳回），提交方看到"待审核"而不是阻塞等待。
  • 批量导入导出：货主侧 CSV 异步任务，失败行单独回执；导出限 1 万行、生成后通知下载，链接 24 小时失效。
  • 快照与版本：线索上的商品快照单独存表，按线索固化；详情页读快照不 JOIN 现势商品，避免商品改价影响历史线索。
  • 归档：已成交 / 已下架超过 90 天的商品转冷表，列表只查热表；冷数据按需回查。
  • 大批量场景的运维手段：商品变更发事件（缓存失效 + 检索增量更新）、按货主维度的批量下架、单货主商品数上限（默认 500 条）防刷。

8.6 多人在线与服务器压力

本产品的访问结构是读多写少、峰谷明显（工作日白天高、夜间低；一条热门货源可能瞬间涌入大量浏览）。降压顺序应是：先缓存、再削峰、最后扩容。

压力来源降压手段不这么做的后果
列表 / 筛选高频读多级缓存 + 检索层 + CDN 静态资源；首页与热门筛选结果缓存 30～120 秒每次筛选都打主库，2000 QPS 直接把连接池打满
详情页突发流量商品详情缓存 + 本地缓存热点 key + 限流；图片走 CDN单条热门货源拖垮整站
站内 IM 长连接独立 WebSocket 网关，单节点按 5 万连接规划；按线索维度订阅，不做全站广播连接数与业务请求互相争抢线程，消息延迟上升
咨询提交瞬间的投递写入后走队列异步投递（outbox）：单条咨询只投管理端，货主侧只更新去重咨询人数与资质分布汇总；短信与企微按频控限速发送同步调企微 API，高峰期提交接口超时，用户以为没提交成功而重复点击
审核与报表异步任务 + 只读副本；看板按小时预聚合，不做实时明细查询报表查询拖慢主库，影响线索写入
恶意刷接口网关限流（IP / 账号 / 接口三维）、验证码、行为风控被脚本刷咨询与响应，坐席被垃圾线索淹没

分级限流基线（可按实际调整）：匿名浏览 60 次/分钟/IP；登录用户读接口 300 次/分钟；咨询提交 10 次/小时/账号；求购需求发布 5 条/天/账号；响应需求 20 次/天/账号；建群 5 次/分钟/坐席。降级预案：检索层不可用 → 降级为 MySQL 单条件查询并关闭聚合计数；短信通道不可用 → 仅站内 + 企微并提示"短信延迟"；非核心看板在高峰期限流或暂停刷新。

容量估算：P0 建议 2 台应用节点 + 1 主 1 从数据库 + 3 主 3 从 Redis + 2 台网关即可支撑 2 万日活、2000 峰值 QPS；扩容优先加应用与网关节点，数据库先加只读副本。

8.7 Redis 缓存分级架构

分级是合理的，但必须按"数据性质"分，而不是按"业务模块"分。本产品的缓存分四级：

层级放什么TTL失效方式
L0 进程内
Caffeine		字典（型号别名、城市、枚举）、排序权重、页面配置、权限角色定义60 秒定时刷新 + 变更广播（Redis pub/sub）主动失效
L1 Redis 热点商品详情、求购需求详情、货主公开信息、咨询热度计数、会话未读数、坐席在线状态5～10 分钟
+ 随机抖动		写后删缓存 + 延迟双删（500ms）
L2 Redis 聚合列表首页、筛选聚合计数、型号建议词、成交热度排行（zset）30～120 秒到期自然失效 + 商品变更事件按维度精准失效
L3 Redis 功能分布式锁、限流计数、幂等键、消息 seq、验证码按用途（秒级～小时级）到期自动清理，不参与业务读取
  • 绝不放缓存的数据：联系方式明文、材料与视频的访问 URL、台账金额与核销状态的唯一真相、权限判定结果（只缓存角色定义，不缓存"某人能看某条线索"的结论）。
  • Key 规范：app:env:module:id[:sub]，例如 app:prod:listing:10231、app:prod:demand:882:summary；禁止无前缀 key，禁止把整表塞进一个 hash。
  • 大 key 与热 key：单 key 值 > 10KB 视为大 key，拆分为字段级 hash 或改存多个小 key；热 key 用 L0 本地缓存 + 逻辑过期兜住，避免单分片被打满。
  • 缓存一致性：以数据库为准，采用 Cache-Aside + 删缓存；商品改价、状态变更、需求关闭都发事件精准失效；商品快照类数据只写不改，天然无一致性问题。
  • 三大故障防护：穿透 → 布隆过滤器 + 空值缓存 60 秒；击穿 → 互斥重建（SETNX）+ 逻辑过期；雪崩 → TTL 加随机抖动 + L0/L1 双层。
  • 实例隔离：纯缓存实例（allkeys-lru，maxmemory 70%）与锁 / 计数 / seq 实例（noeviction，禁用淘汰）必须分开，否则内存紧张时锁被淘汰会导致并发失控。
  • 持久化与高可用：AOF everysec + 主从 + Cluster 3 主 3 从；缓存不可用时业务必须能回源数据库，不允许把 Redis 当唯一存储。
  • 监控指标：命中率目标 > 90%、命中率骤降告警、大 key 扫描、热 key 探测、慢查询、内存碎片率。
分级不合理的情况，本设计已经避开

常见错误有三种：① 只做一层 Redis，热点把单分片打满；② 缓存与锁混用同一实例，内存压力下锁丢失、限流计数丢失；③ 把权限结论与联系方式放进缓存，一次缓存泄露等于一次数据泄露。本设计对应给出三层防线：分层（L0/L1/L2/L3）、分实例（缓存 / 锁）、负向清单（不放什么）。

8.8 服务器与账号安全防护

  • 边界防护：WAF（SQL 注入、XSS、路径穿越）+ CDN 抗静态流量 + DDoS 高防按需开启；管理端使用独立域名、独立证书，默认仅允许办公网 / 白名单 IP 访问，远程办公走 VPN。
  • 身份与登录：密码 + 短信双因子；管理端强制 MFA；登录风控（设备指纹、异地登录、连续失败 5 次锁定 15 分钟）；会话 2 小时过期，敏感操作二次验证。
  • 越权防护：所有查询强制带属主条件（WHERE owner_id = 当前用户 或线索归属校验）；接口级 RBAC 与 5.1 矩阵一一对应；禁止"前端隐藏即视为权限"。
  • 防刷与防爬：注册、咨询、响应三个写入口全部加验证码或行为验证；列表接口返回脱敏字段且限流；对高频遍历 user-agent / IP 段直接封禁；手机验证码 60 秒一次、每日 10 次。
  • 审计：管理端查看联系方式、导出、建群、改状态、改台账全部写审计日志（谁、何时、对哪条线索、做了什么、为什么），日志独立存储、保留 ≥6 个月、不可被业务账号删除。
  • 备份与恢复：数据库每日全量 + 每小时增量，异地保留 30 天；对象存储开版本控制；每季度做一次恢复演练，没有演练过的备份视为不存在。
  • 应急开关：一键停用账号、一键下架商品、一键暂停某坐席建群权限、灰度回滚；应急操作同样留痕。

8.9 加密访问是否可行

可行，且成本可控。分四件事做：

  1. 全站 HTTPS：TLS 1.2+（优先 1.3），HSTS，证书自动续期，HTTP 301 到 HTTPS；移动端禁止明文回退。这是最基础也最容易被漏掉的一项。
  2. 管理端强访问控制：独立入口 + MFA + 白名单 / VPN + 短会话；可选 mTLS（客户端证书）用于财务与超管账号，把"拿到密码"与"能登录"分开。
  3. 字段级加密与密钥管理：联系方式、证件号、验资视频地址按敏感级别加密（AES-256-GCM），密钥托管在 KMS、90 天轮换、与数据分离存储；应用只持有"解密权限"，不持有"密钥本体"。手机号检索走 HMAC 盲索引，支持精确匹配但不可反推、不可批量枚举。
  4. 合规基线：等保 2.0 二级起步（有真实个人信息与合同要素）、个保法要求的最小必要与告知同意、数据分类分级、日志脱敏、删除权响应（账号注销后联系方式 30 天内清除，成交要素按财务留档要求保留）。
三种"看起来加密、实际没用"的做法

① 前端脱敏：接口仍返回明文，只是 UI 打星号——抓包即得。② 可逆加密当脱敏：密钥与应用同库同权限，等于没加密。③ 端到端加密站内 IM：客服无法质检、纠纷无法举证，与本产品"留痕"的核心诉求冲突，不做。
