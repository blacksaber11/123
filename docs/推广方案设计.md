# 算力商机平台 · 推广分佣功能完整设计（v5.1 人工分账交付版）

> 本文件替代 v5.0，一次性给全，不分期、不灰度。
> 本文既是对外可评审的方案，也是开发口径：代码实现以本文为准。
> v5.1 的核心变化：**不做自动分账接口对接**，出款改为人工分账——系统只做审核、生成待打款清单、回填打款结果、记账对账；实际分账 / 转账由财务在微信支付商户平台手动操作。

---

## 0. 可行性结论与能力边界

### 0.0 前置结论：人工分账能不能用（必须先看）

**结论：本期不做自动分账接口对接。分账产品本身的能力边界依然生效，但所有分账 / 转账动作都由财务在微信支付商户平台手动完成。**

依据（微信支付口径，对人工操作同样成立）：

| 事实 | 影响 |
| --- | --- |
| 分账要求下单时传 `settle_info.profit_sharing = true`，之后凭 `transaction_id` 发起分账 | 普通 JSAPI / APP / 扫码支付可满足；虚拟支付订单大概率不带该标记 |
| 分账资金最长冻结 180 天，超期自动解冻 | 佣金必须在支付后 180 天内分完 |
| 单笔订单分账总额默认 ≤ 订单金额 × 30% | 佣金比例必须受此约束 |
| 分账接收方需先添加（`PERSONAL_OPENID`） | 开通推广后由财务在商户平台添加 |
| 已分账订单退款必须先做「分账回退」 | 退款链路多一步，回退失败会卡退款 |
| 小程序虚拟支付（`wx.requestVirtualPayment`）订单不走普通微信支付下单流程 | 虚拟支付订单没有 `profit_sharing` 标记，通常不能分账，只能走转账 |

因此人工出款有两条路径。**默认只走路径 B**：订单资金不冻结，平台只留佣金部分，其余资金随时可取用。

| 路径 | 适用订单 | 财务在商户平台的操作 | 回填单据号 |
| --- | --- | --- | --- |
| 路径 B（默认） | 全部订单（微信 / 虚拟支付 / iOS） | 手动发起「商家转账到零钱」 | 转账单号 |
| 路径 A（可选，默认关闭） | 仅当开启 `splitEnabled` 且下单带 `profit_sharing=true` | 对该笔原订单手动发起「分账」 | 分账单号 |

> 路径 A 会把整笔订单资金冻结最长 180 天，与「只留佣金、其余随时可取」冲突，因此默认关闭，只在确有锁定资金需求时开启。

> 系统不区分 A / B 的实现差异，只要求回填「单据号 + 实际出款金额 + 出款时间 + 凭证」，统一记入台账。
> **待实测：能否在商户平台对虚拟支付订单手动发起分账。** 若不能，则该类订单全部走路径 B（手动商家转账）。
> 这个结论不影响系统设计：状态机、台账、对账对两条路径完全一致，只是财务在商户平台点的按钮不同。

### 0.1 结论

| 项目 | 结论 |
| --- | --- |
| 出款方式 | **人工出款**；系统不调用任何分账 / 转账 API |
| 资金是否冻结 | **不冻结**。默认不开分账，订单资金 T+1 正常结算到商户号基本账户，可随时提现 / 取用；只有佣金在台账上预留 |
| 路径 B（默认） | 财务在商户平台手动「商家转账到零钱」，覆盖全部订单（微信 / 虚拟支付 / iOS） |
| 路径 A（可选，默认关闭） | 仅当明确开启 `splitEnabled` 时使用；开启后该订单整笔资金被冻结最长 180 天，与「只留佣金」冲突，非必要不开 |
| 资金路径 | 用户支付 → 商户号结算 → 审核通过 → 生成待打款单 → 财务商户平台操作 → 回填 → 校验 → 核销到账 |
| 是否需要二级商户号 | 不需要 |
| 平台收入 | **会员付费 − 佣金净额**；5% 手续费只是把佣金打折，不单列为收入 |
| 佣金比例 | **平台统一设置**，默认 20%，上限 30%，推广者不可改 |
| 冻结规则 | 佣金**台账冻结**（不是资金冻结）：次月 15 日 00:00 前不可申请；Apple 渠道等确认到账后才解冻 |
| 打款时间 | **无固定打款日**；审核通过后进入「待打款」，由财务按清单执行 |
| 提现审核 | **必须人工审核**；审核通过后不再做业务拦截 |
| 到账 | 以财务回填的单据号与出款时间为准，系统校验通过即「已到账」 |
| 最低提现 | 100 元，无阶梯 |
| 单笔上限 | 20,000 元（毛额，转账通道硬限制；分账同口径约束） |
| 个税 | `taxEnabled` 默认关闭；开启后按劳务报酬预扣 |

### 0.2 与 v5.0 的差异（自动分账 → 人工分账）

| 项 | v5.0（自动分账） | v5.1（人工分账） |
| --- | --- | --- |
| 出款执行 | 后台任务调用分账 / 转账接口 | **财务在商户平台手动操作**，系统只做清单与台账 |
| 出款通道 | 分账为主 + 转账兜底，系统自动切换 | 路径 A 手动分账 / 路径 B 手动转账，财务按订单选择 |
| 提现状态 | 待审核 / 处理中 / 已到账 / 失败 | **待审核 / 待打款 / 打款中 / 已到账 / 打款失败**（旁支：已驳回 / 已撤销） |
| 审核后动作 | 自动生成计划并执行 | 生成待打款单 + 出款明细，等财务领取执行 |
| 到账判定 | 微信接口终态 | **财务回填 + 系统校验**（明细合计、单据号唯一、幂等） |
| 失败处理 | 自动重试 / 自动换通道 | 保持占用，人工「重新打款」或「退回余额」 |
| 超时提醒 | 无 | 待打款超 24 小时中台标红 + 审计留痕 + 推广者进度提醒 |
| 双人复核 | 无 | 金额 ≥ 5,000 元必须第二人复核（可配） |
| 对账 | 校验接口终态 | **导入商户平台账单 / 分账记录**与系统明细比对，输出差异单 |
| 自动分账 API | 本期实现 | **本期不做**；保留 `payoutMode='auto'` 开关，默认关闭 |

### 0.3 能力边界

| 能力项 | 状态 | 本方案处理 |
| --- | --- | --- |
| 微信支付分账 | 要求普通支付订单 + 已开通分账产品 | 只作为人工操作的前置条件，系统不调用接口 |
| 分账接收方 | 需提前添加，个人接收方需 openid（建议同时传实名） | 开通后由财务在商户平台添加；未添加则该用户走路径 B |
| 分账比例上限 | 默认 30%，可在商户平台申请调整 | 平台比例 ≤ 30%，出款金额 ≤ 佣金 × 95%，天然留出余量 |
| 分账 180 天期限 | 超期自动解冻 | 150 天预警；超期订单只能走路径 B |
| 已分账退款 | 必须先分账回退 | 财务在商户平台手动回退，失败转人工 |
| 商家转账 | 企业主体 + 场景报备「佣金报酬」 | 默认唯一出款通道，必须开通 |
| 单笔 > 20,000 | 不支持，拆单属违规 | 直接拒绝 |
| 个人 / 个体户主体 | 不能做商家转账 | 必须企业主体 |
| 提现手续费 | 微信侧不收费 | 平台自收 5%，属业务规则 |
| 自动分账 API | 本期不实现 | `payoutMode='auto'` 仅保留开关，默认关闭 |

## 1. 角色、入口与状态

### 1.1 角色

| 角色 | 说明 | 关键约束 |
| --- | --- | --- |
| 普通用户 | 未开通推广 | 分享不带推广标识，不产生绑定 |
| 推广者 | 已签协议、`promoterStatus=active` | 分享带 `ref`，可计佣、可提现 |
| 被邀请人 | 已绑定某推广者 | 首次登录绑定，永久不可改绑 |
| 客服 | 中台坐席 | 只读推广数据，无审核 / 出款权 |
| 财务 | 中台财务 | 提现审核、领取并执行打款、回填单据、异常处理 |
| 管理员 | 平台超管 | 全部动作，含比例、封禁、手工冲正 |

### 1.2 入口（只新增 1 个页面）

| 位置 | 形态 | 说明 |
| --- | --- | --- |
| 小程序「我的」 | 「推广中心」入口行 | 未开通显示「分享赚钱」，已开通显示累计收益 |
| 小程序 `pages/promote/promote` | 新页面 | 推广中心，全部推广操作都在此页完成 |
| 任意页面右上角分享 | 全局注入 `ref` | 由 `app.js` 统一包装，不逐页改造 |
| 中台导航 | 「推广管理」 | 管理员 / 财务可见 |
| 中台工作台 | 待办卡片 | 待审核提现、待打款超 24 小时、打款失败、对账差异 |
| 中台用户详情抽屉 | 「推广信息」区块 | 绑定关系、平台比例、余额、欠款、提现记录 |

### 1.3 核心状态

```text
推广者：none（未开通）→ active（正常）→ blocked（封禁）

佣金：  待结算 ──次月15日00:00──→ 可提现 ──核销──→ 已提现
           └──────── 任意阶段退款 ────────→ 已冲正

提现：  待审核 ──审核通过──→ 待打款 ──财务领取──→ 打款中 ──回填校验通过──→ 已到账
           │                   │                   │
           │                   │                   ├──回填失败──→ 打款失败（保持占用）
           │                   │                   │                ├──重新打款──→ 打款中
           │                   │                   │                └──退回余额──→ 已撤销
           │                   └──退回余额──→ 已撤销
           ├──驳回──→ 已驳回
           └──用户撤销──→ 已撤销
```

> 「处理中」不再使用：审核已通过、等待财务执行 = **待打款**；财务已领取、正在操作 = **打款中**（可选，用领取锁防重复操作）。
> 人工分账没有「待确认」状态；路径 B 若用商家转账，以商户平台显示的状态为准，由财务回填时人工确认。

## 2. 资金链路

### 2.1 资金流（默认不冻结，只留佣金）

**默认路径 B（覆盖全部订单：微信 / 虚拟支付 / iOS）：**

```text
用户支付 999
  → 下单不传 profit_sharing，订单资金不进分账冻结，T+1 正常结算到商户号基本账户
  → 基本户余额可随时提现 / 取用，平台只需自己留够「应留存佣金」（见下表）
  → 实时计佣：base = 999 − 9.99 = 989.01，比例 20% → 佣金毛额 197.80（只记台账，不动资金）
  → 佣金台账冻结至次月 15 日 00:00（Apple 渠道等平台确认到账，见 3.5）
  → 用户申请 → 财务人工审核
  → 审核通过 → 生成待打款单与出款明细，状态「待打款」
  → 财务领取 → 商户平台手动发起「商家转账到零钱」
  → 财务回填转账单号与金额 → 系统校验通过 → 「已到账」+ 核销佣金
  → 手续费与个税不出款，留在商户号
```

**要留多少现金（重点：只留佣金部分）**

| 佣金状态 | 是否留现金 | 原因 |
| --- | --- | --- |
| 待结算（未到 15 日 / Apple 未确认到账） | **不用** | 还没到付款义务；期间订单退款，佣金直接冲正，不产生支出 |
| 可提现、尚未申请 | **要** | 用户随时可能发起申请 |
| 提现中（待审核 / 待打款 / 打款中） | **要** | 已占用，这笔钱一定会出 |
| 已冲正欠款 | **不用** | 后续佣金自动抵扣 |

> **应留存现金 = 可提现余额 + 提现中金额**，中台「推广统计」直接可查（`available` + `withdrawing`），其余结算资金可随时取用。
> 例外提醒：订单退款是从商户号余额扣的，余额被提空会导致退款失败（余额不足）。建议留一小笔退款缓冲，或退款前先回充，这不属于佣金预留。

**路径 A（可选，默认关闭）：**

```text
用户支付 999
  → 下单带 profit_sharing=true，该笔订单整笔资金被冻结（最长 180 天），期间不可提现
  → 实时计佣 197.80，冻结至次月 15 日
  → 财务在商户平台对该订单手动「分账」出佣金净额 187.91
  → 回填分账单号 → 核销 → 佣金结清后完结分账，解冻剩余资金
```

> 路径 A 的价值是「专款专用、佣金一定有现金可出」，代价是整笔订单资金 180 天不可动用。
> 与本方案「只留佣金、其余随时取用」的口径冲突，因此 `splitEnabled` **默认 false**；只有明确想把资金锁住时才开启。

### 2.2 平台收入口径（重点）

**平台收入 = 会员实付 − 佣金净额。5% 手续费不单列为收入，它只是把佣金毛额打折。**

| 科目 | 公式 | 999 元示例 |
| --- | --- | --- |
| 会员实付 | P | 999.00 |
| 通道成本 | `C = P × 通道费率`（微信 1%） | 9.99 |
| 计佣基数 | `base = P − C` | 989.01 |
| 佣金毛额 | `G = base × 平台比例`（20%） | 197.80 |
| 手续费（内部折让） | `F = G × 5%` | 9.89 |
| 佣金净额（用户实得） | `N = G − F` | 187.91 |
| **平台收入（业务口径）** | **`P − N`** | **811.09** |
| 平台实际留存（现金） | `P − C − N` | 801.10 |

口径说明：

- 对外与财务只报「平台收入 = 实付 − 佣金净额」，不再把 5% 手续费列为收入项；
- 5% 手续费的价值体现为「佣金净额 < 佣金毛额」，因此已隐含在平台收入里；
- 平台实际留存 = 平台收入 − 通道成本，二者差额只由通道费率产生；
- 出款时只出 `N`，`G − N` 留在商户号余额中（默认不开分账，资金不冻结），不计入平台收入科目。

### 2.3 三本账，必须分开

| 账本 | 记账对象 | 用途 |
| --- | --- | --- |
| 佣金账本 | `commissions`（每笔订单一条） | 算谁该拿多少、是否已核销、是否被冲正 |
| 现金账本 | `promoterWithdrawals`（每次提现一条） | 算冻结了多少、打了多少、失败多少 |
| 出款明细账 | `promotePayoutItems`（每个出款分项一条） | 对账用：哪笔佣金、哪个订单、出款多少、单据号与终态 |
| 用户汇总 | `users.promoter*` | 只做展示加速，**不得作为唯一依据** |

铁律：用户余额由佣金账本推导，提现占用由现金账本推导，出款金额由明细账汇总；三者每日对账，不一致即冻结。

### 2.4 通道成本与计佣

```text
通道费率 channelRate = 微信支付 1% / iOS 12%
（代码常量 channelFeeRate，改费率需改代码发版；已计佣按落库快照不追溯）
通道成本 C = round2(实付 P × channelRate)
计佣基数 base = round2(P − C)
佣金毛额 G = round2(base × 平台统一比例)
佣金净额 N = round2(G × (1 − 5%))
```

示例（会员 999 元，平台比例 20%）：

| 通道 | 实付 | 通道成本 | 基数 | 佣金毛额 | 手续费 | 佣金净额 | 平台实际留存 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 微信 JSAPI | 999 | 9.99 | 989.01 | 197.80 | 9.89 | 187.91 | 801.10 |
| 虚拟支付 / iOS | 999 | 119.88 | 879.12 | 175.82 | 8.79 | 167.03 | 712.09 |

> 佣金永远从「扣完成本后的基数」里出；平台在任何比例下都不亏。

### 2.5 手续费定位

| 问题 | 口径 |
| --- | --- |
| 向谁收 | 不向用户额外收费，只从推广者佣金里扣 |
| 何时扣 | 佣金转「可提现」时计提，提现时兑现 |
| 怎么记账 | `feeAmount = G − N`，留在商户号；不计入平台收入科目 |
| 能否改 | 后台可调；已计佣的历史订单按当时的费率快照，不追溯 |
| 与分账的关系 | 分账只分 `N`；`F` 不出款，避免触碰 30% 比例上限 |

### 2.6 两条出款路径的选择

**默认只走路径 B**（`splitEnabled=false`）：订单资金不冻结，平台只留佣金，其余随时可取。

| 判断条件 | 路径 A（手动分账，仅开启时） | 路径 B（手动转账，默认） |
| --- | --- | --- |
| `splitEnabled=false`（默认） | — | ✅ 全部订单 |
| 订单有 `transaction_id` 且下单带分账标记 | ✅ | — |
| 支付未满 180 天 | ✅ | — |
| 接收方已添加且 openid 有效 | ✅ | — |
| 虚拟支付 / iOS 订单 | — | ✅ |
| 支付已超 180 天（资金已解冻） | — | ✅ |
| 商户平台提示该订单不可分账 | — | ✅ |

原则：**默认路径 B，资金不进冻结；只有明确开启 `splitEnabled` 且订单可分账时才走 A。** 系统只记录最终单据号，不关心财务选了哪条。

## 3. 产品规则

### 3.1 开通

```text
我的 → 推广中心 → 阅读《推广服务协议》
  → 勾选同意 → 填真实姓名 → 立即开通
  → 生成推广码（分账接收方由财务后续在商户平台添加）
```

硬性条件：

- `agreed === true` 且协议版本与服务端一致；
- 已登录、已授权手机号、账号状态正常；
- 近 90 天有退款风险标记的账号不可开通；
- 必须填写真实姓名（分账接收方与 ≥ 2,000 元转账都需要），加密存储、只回显脱敏；
- 财务未完成接收方添加不阻断开通，该用户标记 `splitReceiverReady=false`，其提现只走路径 B（手动商家转账），并在推广中心提示「补全信息后可使用更快到账」；
- 协议版本升级后，未重签者**只暂停提现**，计佣继续。

### 3.2 佣金比例（平台统一）

| 项 | 规则 |
| --- | --- |
| 设置方 | **平台统一设置**，中台「推广管理 → 规则配置」 |
| 范围 | 5%–30%，步进 0.1%，默认 20% |
| 推广者 | **只读展示，无修改入口**；`promote.setRate` 接口删除 |
| 生效 | 修改后**新支付的订单**用新比例，历史佣金不变 |
| 快照 | 每笔佣金落库时记录当时的比例与费率 |
| 分账约束 | 必须满足 `ratio × 95% ≤ 30%`（30% 比例时为 28.5%），超出拒绝保存 |
| 兜底 | 若商户平台分账比例上限被下调，系统按 `maxSplitRatio` 告警，财务对该类订单改走路径 B |

### 3.3 分享与绑定

| 场景 | 行为 |
| --- | --- |
| 未开通时分享 | 不带 `ref`，永不绑定、永不追溯 |
| 开通后分享任意页面 | 统一追加 `ref=推广码`，支持朋友圈 / 群 / 私聊 |
| 新用户首次登录 | 带 `ref` 则绑定，先到先得 |
| 已登录老用户点分享链接 | 登录态命中也要校验 `ref`，未绑定则补绑（只补一次） |
| 已绑定用户再点别人链接 | 忽略，不弹提示，不改绑 |
| 绑定自己 | 拒绝 |
| 推广者未激活 / 被封禁 / 高风险 | 不绑定 |
| 绑定时间晚于支付时间 | 该笔不计佣 |
| 绑定时间早于推广者开通时间 | 该笔不计佣 |

绑定关系落在 `referralBindings`，`id = uid` 唯一索引，天然保证一人一条、不可改绑。

### 3.4 实时计佣

- 被邀请人**每一笔**会员支付成功即写一条 `commissions`，状态「待结算」，推广者立即可见；
- 同时记录 `channel`、`transactionId`（用于判断优先走哪条出款路径）、`rate`、`feeRate` 快照；
- `paymentId` 唯一索引，重复回调不会重复计佣；
- 计佣失败不阻断支付主流程，由每日补偿任务补齐；
- 退款后按 3.9 节冲正。

### 3.5 冻结与可提现（次月 15 日）

```text
eligibleAt = 支付时间所属月份的「次月 15 日 00:00（北京时间）」
```

| 支付时间 | 可申请提现时间 |
| --- | --- |
| 11-01 10:00 | 12-15 00:00 |
| 11-15 23:59 | 12-15 00:00 |
| 11-16 09:00 | 12-15 00:00 |
| 11-30 23:00 | 12-15 00:00 |
| 12-01 00:10 | 次年 01-15 00:00 |

- 冻结期内状态为「待结算」，**不可提前、不可部分解冻**；
- 每日 01:00 结算任务把 `eligibleAt ≤ now` 的佣金批量转「可提现」，同时自动抵扣欠款；
- 15 日之后**随时可申请**，不再有统一打款日，也不存在「申请顺延下月」；
- **Apple 渠道（iOS）例外**：不看日历日期，佣金冻结到「平台确认该月 Apple 结算款到账」为止。Apple 的钱由 Apple 按月结算（月末后 30 天以上）才到平台账户，期间还可能发生 Apple 退款；钱到账前解冻，等于用平台自有资金垫付可能被退回的佣金。财务 / 管理员在中台「确认 Apple 到账」（`promote.appleSettle`，按支付月份）后，该月冻结佣金才解冻为可提现（解冻时同口径自动抵扣欠款）。开关 `appleArrivalHold` 可关闭（关闭后新产生的 Apple 佣金回到次月 15 日口径；已标记 `arrivalHold` 的存量佣金不会自动解冻，仍需按月在 `promote.appleSettle` 确认）。

### 3.6 提现规则

| 项 | 规则 |
| --- | --- |
| 最低 | 100 元 |
| 阶梯 | 无 |
| 单笔上限 | 20,000 元（毛额） |
| 单用户单日 | 20,000 元（按实际出款净额累计；路径 A 与路径 B 合并计算） |
| 商户单日 | 手动商家转账单日 100,000 元，超限顺延次日；手动分账不受此限（以商户平台实际额度为准） |
| 手续费 | 5%，按毛额计，最低 0.01 元 |
| 个税 | `taxEnabled=false` 时不扣；开启后按劳务报酬累计预扣 |
| 欠款抵扣 | 申请时自动抵扣，抵扣后净额必须 > 0 |
| 欠款上限 | `promoterDebt > 500` 禁止提现，转人工 |
| 频率 | 每人每日最多 3 次申请，同一时间只允许 1 笔未完结提现（待审核 / 待打款 / 打款中） |
| 可申请时间 | `eligibleAt` 之后随时 |
| 审核 | **必须人工审核** |
| 到账 | 以财务回填的出款时间为准；路径 B 是否需用户确认以商户平台为准 |

提现计算：

```text
gross ∈ [100, min(20000, available)]
fee   = round2(gross × 5%)
tax   = taxEnabled ? 按税款所属期累计计算 : 0
deductToDebt = min(debt, round2(gross − fee − tax))
net   = round2(gross − fee − tax − deductToDebt)，必须 > 0
```

### 3.7 人工审核

| 项 | 规则 |
| --- | --- |
| 审核角色 | 财务 / 管理员 |
| 审核要素 | 实名一致、无风险标记、协议有效、佣金来源正常 |
| 批量 | 支持批量通过，逐笔留审核人、时间、意见 |
| 驳回 | 必须填原因，毛额立即释回 `available` |
| 审核后 | **审核通过即放行，不再做业务拦截**（不再校验比例、欠款、限额、协议） |
| 后续 | 生成待打款单与出款明细，状态「待打款」，等财务领取执行 |
| 分离 | **审核与执行分离**：审核人不得回填同一笔；金额 ≥ 5,000 元时复核人不得是审核人、执行人 |
| 时效 | 建议 1 个工作日内完成，超 24 小时未审核在中台标红 |

### 3.8 审核通过后的待打款与人工执行

```text
审核通过 → 状态「待打款」→ 生成出款明细（逐佣金分配）
  → 财务在「待打款」Tab 点「领取」→ 加锁，状态「打款中」，其他人不可再操作
  → 导出打款清单 CSV → 到商户平台手动操作
      ├─ 路径 A：对该笔原订单发起分账
      └─ 路径 B：发起商家转账到零钱
  → 回到中台「回填」：单据号、实际出款金额、出款时间、凭证截图、备注
  → 系统校验通过 → 「已到账」+ 核销佣金 + 汇总更新 + 站内信
  → 校验不通过 → 回填失败，状态保持「打款中」，按提示修正后重新回填
```

出款明细生成规则：

- 按佣金 `createdAt` **FIFO** 选未核销佣金，直到覆盖 `gross`；
- 按毛额比例把 `net` 分配到各佣金，尾差用最大余数法补齐，保证 `Σ 分项 = net`；
- 每条明细金额必须 ≥ 0.01，且 ≤ 对应佣金的可用净额；
- 明细一次性落库到 `promotePayoutItems`，状态 `todo`；同一 `commissionId` 只能有一条 `todo / doing` 明细；
- 领取用条件更新加锁（`status: 待打款 → 打款中`，同时写 `claimedBy`），影响行数为 0 即表示已被他人领取。

回填校验（五项全部通过才可置「已到账」）：

| 校验 | 规则 | 不通过提示 |
| --- | --- | --- |
| 金额闭合 | `Σ 明细金额 = 可用明细合计`（`net − uncoveredAmount`）；无冲正时即等于 `net`，误差必须为 0 | 「明细合计与可用明细合计不一致，请核对」 |
| 明细上限 | 每笔明细 ≤ 对应佣金的可用净额 | 「第 N 笔明细超出该佣金可用净额」 |
| 单据号唯一 | 分账单号 / 转账单号全局唯一 | 「该单据号已被使用」 |
| 幂等 | 同一提现重复回填直接返回首次结果 | 前端提示「已回填，无需重复提交」 |
| 双人复核 | 金额 ≥ 5,000 元须第二人复核，复核人 ≠ 审核人 ≠ 执行人 | 「大额出款需第二人复核」 |

> 未回填不核销、不释放占用。审核通过超过 24 小时仍未回填，中台标红 + 站内信提醒财务。

### 3.9 退款与冲正

业务退款窗口为支付后 7 天，早于「次月 15 日」可提现日，因此**正常退款不会撞上已出款**；只有特批退款、投诉退款、Apple 退款才会命中已出款佣金。

| 佣金状态 | 冲正动作 |
| --- | --- |
| 待结算 | 直接置「已冲正」，扣 `pending` |
| 可提现（未核销 / 未出款） | 扣 `available`，佣金置冲正，冻结资金不动 |
| 可提现（已部分出款） | 财务在商户平台手动分账回退；未出款部分扣 `available` |
| 已提现（分账路径已到账） | 先由财务在商户平台手动发起分账回退；成功则无欠款，失败则欠款 += 已出款净额 |
| 已提现（转账路径已到账） | 欠款 += 该笔净额 |
| 已冲正 | 幂等返回，不重复扣 |

分账回退规则：

```text
对该佣金每一笔成功的出款（promotePayoutItems）
  → 财务在商户平台按原分账单号发起「分账回退」
  → 回退成功后，把回退单号回填到系统
  → 回退成功：原订单可退金额恢复，佣金置「已冲正」
  → 回退失败（接收方零钱不足 / 账户异常）：退款挂起，记欠款，站内信 + 中台告警
```

铁律：

- **未完成分账回退，不得把订单标记为退款成功**（否则退款金额受限或平台倒挂）；
- **同一笔佣金不得同时被核销和冲正**，冲突时冲正优先，核销让位并告警；
- 分账回退失败只能转人工，不允许「先退款、欠款以后再说」的自动处理。

冲正前必须先处理未完结的提现单：

| 提现单状态 | 处理 |
| --- | --- |
| 无未完结提现 | 直接冲正 |
| 待审核 | 先取消提现（毛额退回 `available`），再冲正 |
| 待打款 / 打款中（已生成明细，尚未回填） | 冲正照常（未出款不记欠款，明细对应毛额已从可用划入「提现中」，冲正不再重复扣减可用）；提现单继续走终态，核销跳过已冲正佣金，差额记 `uncoveredAmount` 并告警；整单明细全部失效时财务「退回余额」只释放未被冲正的毛额 |
| 已到账 | 已分账先由财务手动回退，回退失败记欠款净额 |

### 3.10 封禁、停用、注销

| 场景 | 处理 |
| --- | --- |
| 封禁 | 停止计佣；待结算冻结；待审核提现驳回释放；待打款 / 打款中只走终态 |
| 停用 | 同封禁；用户无法登录，打款中未回填的由财务「退回余额」释放 |
| 协议未重签 | 只暂停提现，计佣继续 |
| 申请注销 | 有未完结提现、欠款 > 0、可提现余额 > 0 时禁止自助注销，转人工结清 |
| 注销后待结算 | 冻结期满无可收款账户的转平台留存，协议中写明 |

## 4. 资金安全

### 4.1 十个不变式（每日对账逐条校验）

| 编号 | 不变式 |
| --- | --- |
| I1 | `pending = Σ 待结算佣金.amount` |
| I2 | `available = Σ(可提现佣金.amount − withdrawnAmount − offsetToDebt)`，且 ≥ 0 |
| I3 | `withdrawing = Σ(待审核 + 待打款 + 打款中 + 打款失败).amount`（毛额，全部占用余额） |
| I4 | `withdrawn = Σ 已到账提现.amount`（毛额） |
| I5 | `earning = pending + available + withdrawing + withdrawn + appliedToDebt` |
| I6 | 每笔佣金被占用 / 已出款金额 ≤ `round2(amount × 95%)`；同一订单累计出款 ≤ `round2(实付 × 30%)` |
| I7 | 欠款只由冲正产生；抵扣不得把 `available` 扣成负数，`promoterDebt` 不得为负 |
| I8 | 已到账提现 `net = Σ 成功出款明细.amount`，且 `amount − net = fee + tax + deductToDebt`（误差 ≤ 0.01） |
| I9 | **一笔佣金只能被一个有效出款明细占用**（唯一索引 `activeCommissionKey`：todo / doing / failed 时等于 `commissionId`，终态为唯一退休键 `R#<明细 id>`） |
| I10 | `users.promoter*` 汇总只做展示，**一切以佣金账本与出款明细账为准** |

补充校验（不构成资金口径，但对账必查）：

- 已到账提现的 `Σ 明细金额` 必须与 `net` **精确相等**，不等即差异单；
- 每条出款明细必须能对应到一笔提现与一笔佣金；
- 已到账提现必须有回填单据号，单据号重复或查不到即差异单；
- 已解冻订单的 `冻结余额 = 实付 − 已出款 − 已解冻` 必须为 0。

### 4.2 原子性、并发与幂等

| 风险 | 手段 |
| --- | --- |
| 同时两笔提现 | `promoterWithdrawals.activeKey = uid` 唯一索引；终态改写唯一退休键 `R#<提现单 id>` 释放（不可置 `NULL`） |
| 重复提交 | 客户端 `requestId` + 服务端唯一索引 |
| 重复计佣 | `commissions.paymentId` 唯一索引 |
| 重复占用佣金 | `promotePayoutItems.activeCommissionKey` 唯一（todo / doing / failed 等于 `commissionId`，终态唯一退休键） |
| 两人同时领取 | `待打款 → 打款中` 条件更新 + 写 `claimedBy`，影响行数为 0 即已被领取 |
| 重复回填 | 提现单 `payoutRequestId` 幂等；已到账再次回填直接返回首次结果 |
| 重复单据号 | `payoutNo` 全局唯一索引 |
| 重复核销 | 佣金 `withdrawnAmount` 条件更新，且不得超过 `amount` |
| 重复回退 | `refundNo` 唯一；回退成功才置冲正 |
| 重复结算 | `待结算 → 可提现` 条件更新，影响行数为 0 直接返回 |
| 余额被扣成负数 | 所有扣减带 `>= amount` 条件，影响行数为 0 即失败 |
| 回填中途中断 | 校验与落账在同一个幂等 handler 内完成，失败可按 `payoutRequestId` 安全重试 |

存储层没有事务，所有跨表操作按「先占用 → 再写明细 → 最后写汇总」的顺序，任一步失败由人工重试或补偿任务按幂等键重放。

### 4.3 终态判定（最关键的一条）

```text
人工分账 / 人工转账：
  财务在商户平台操作成功 ≠ 系统已知
    ├─ 回填：单据号 + 金额 + 时间 + 凭证 → 五项校验通过 → 「已到账」+ 核销
    ├─ 回填：校验不通过 → 拒绝落账，状态保持「打款中」，提示修正
    ├─ 财务标注失败 → 「打款失败」，保持占用，可重新打款或退回余额
    └─ 超 24 小时未回填 → 中台标红 + 站内信，不改变状态、不释放占用
```

- 绝不把「财务口头说已打款」或「商户平台显示成功」直接当已到账，必须有回填；
- 回填单据号必须能在商户平台查到，对账时逐笔比对；
- 同一提现重复回填按幂等处理，不重复核销；
- 回填与冲正可能并发，写终态一律用条件更新；
- `payoutMode='auto'` 本期不实现，当前只有人工分支。

### 4.4 提现状态机

| 状态 | 占用余额 | 动作 |
| --- | --- | --- |
| 待审核 | 是 | 审核通过 → 待打款 / 驳回 / 用户撤销 |
| 待打款 | 是 | 已生成明细，等财务领取；超 24 小时标红 |
| 打款中 | 是 | 财务已领取（加锁），商户平台操作后回填 |
| 已到账 | 否（已核销） | 终态 |
| 打款失败 | 是 | 重新打款（回「打款中」）/ 人工退回余额 |
| 已驳回 | 否 | 释回 `available` |
| 已撤销 | 否 | 用户撤销或财务退回余额，释回 `available` |

### 4.5 出款失败与人工处理

```text
路径 A 手动分账失败（不可分账 / 接收方异常 / 比例超限）
  ├─ 改走路径 B（手动商家转账），同一提现单继续
  ├─ 退回余额：明细置 cancelled，提现置「已撤销」，占用释放
  └─ 记录失败原因，中台告警

路径 B 手动转账失败（限额 / 账户异常 / 用户未确认）
  ├─ 修正后重新打款 → 回「打款中」
  └─ 仍失败 → 人工「退回余额」，或挂起等用户补全信息

任何情况下：失败不自动释放占用，只有人工显式「退回余额」才释放。
回填内容填错不落账，按提示修正，不产生第二笔占用。
```

### 4.6 欠款

- 只由冲正产生，按用户**实收净额**记，不按毛额；
- 结算时自动抵扣：`deduct = min(debt, 本次转可提现金额)`，写入 `offsetToDebt` 与 `appliedToDebt`；
- 提现时再次兜底抵扣，抵扣后净额必须 > 0；
- 欠款 > 500 元禁止提现，转人工；
- 欠款必须有明细来源（哪笔订单、哪次冲正），不允许手工凭空加减；
- 分账回退失败产生的欠款，需在明细中标记 `source=splitRefundFailed`。

### 4.7 180 天与冻结资金（仅路径 A 适用）

> 默认 `splitEnabled=false`，下单不带 `profit_sharing`，不存在订单资金冻结，本节整段不生效。
> 只有明确开启路径 A 时，才按下列节奏处理被冻结的整笔订单资金。

| 时间点 | 动作 |
| --- | --- |
| 支付后 150 天 | 扫描仍未结清的佣金，站内信提醒用户，中台列入待办 |
| 支付后 170 天 | 再次提醒，财务可主动联系用户 |
| 支付后 180 天 | 微信自动解冻，标记 `splitExpired=true`，后续只能走路径 B |
| 佣金全部结清 | 财务在商户平台完结该订单分账，解冻剩余资金 |

- 完结分账只在该订单下所有佣金都已核销或已冲正时操作；
- 部分提现导致佣金未结清的，不提前完结，避免剩余佣金无法分账；
- 每次解冻 / 完结都要落 `promotePayoutItems`（type=unfreeze），用于对账。

### 4.8 对账与告警

每日 02:00 执行，结果写 `promoteReconciliations`：

1. 导入商户平台前一日账单、分账记录、转账记录；
2. 逐用户校验 I1–I5、I7–I10，差异 > 0.01 元 → 标记 `drift`，冻结该用户提现；
3. 校验 I6：逐佣金比对已出款金额与佣金毛额 × 95%、订单实付 × 30%；
4. 逐笔比对回填单据号与商户平台记录：金额、时间、收款方必须一致；
5. 校验每笔已到账提现都有完整出款明细，且明细金额之和**精确等于** `net`；
6. 校验已解冻订单的冻结余额为 0；
7. 校验退款单与手动分账回退一一对应，未回退的退款单必须处于挂起状态；
8. 任何一项不平 → 输出差异单，中台告警，人工核对后清零。

### 4.9 风控

| 规则 | 阈值 | 动作 |
| --- | --- | --- |
| 自买自返 | 同 `uid` / 同设备 / 同实名 | 不计佣，标记风险 |
| 批量注册 | 同一推广者 24h 内绑定 > 20 个新号 | 暂停该推广者计佣，人工审核 |
| 高退款率 | 近 30 天退款率 > 30% | 暂停提现，人工审核 |
| 异常提现 | 当日申请达到 3 次，或频繁修改实名 | 下次提现转人工复核 |
| 设备聚集 | 同一设备绑定 ≥ 3 个账号 | 标记风险，佣金挂起 |
| 分账回退失败 | 任意一笔 | 中台告警，该用户后续只走路径 B |

### 4.10 合规红线

- 分账必须有真实交易背景，不得为他人套现、代收代付；
- 分账接收方必须为推广者本人，实名与 openid 一致；
- 虚拟支付订单不得包装成普通支付套用分账；
- 人工分账必须留档：单据号、金额、时间、凭证截图、审核人 / 执行人 / 复核人；
- 佣金记录、提现记录、出款明细、回执凭证、协议签署至少留存 5 年；
- 协议必须写明：平台统一比例、冻结规则（次月 15 日）、手续费、个税、退款追偿、封禁规则、注销处理；
- 不得对用户承诺「保本」「稳赚」，不得诱导贷款参与。

## 8. 全链路时序

### 8.1 分享与绑定

```text
推广者 A 开通 → 生成 refCode → 分享任意页面（自动追加 ref）
  → 新用户 B 打开 → app.js 捕获 ref → 登录时带 ref
  → 服务端校验：A 已开通 / 未封禁 / 非 B 自己
  → referralBindings 写入 id=B，唯一索引保证只绑一次
  → 已绑定用户再点任何链接：直接忽略
```

### 8.2 下单与支付

```text
B 下单会员
  → 微信 JSAPI 下单（可分账场景）：settle_info.profit_sharing = true
  → 用户支付成功 → 微信回调 / 主动查单确认
  → 落 payments（paymentId、transactionId、channel、amount）
  → 虚拟支付 / iOS：走原通道，无 transactionId
```

> `profit_sharing=true` 必须在**下单时**传，事后补传无效。它决定该订单能否走路径 A，不影响人工出款流程本身。

### 8.3 支付计佣

```text
支付成功（幂等）
  → 查 B 的绑定关系与 A 的状态
  → 校验 boundAt ≤ paidAt、paidAt ≥ A.promoterOpenedAt
  → 读平台比例与费率 → 计算 C / base / G / F / N
  → 写 commissions（paymentId 唯一，eligibleAt = 次月 15 日）
  → 更新 A 的 promoterPending / promoterEarning
  → 站内信：佣金到账（待结算）
```

### 8.4 结算（次月 15 日）

```text
每日 01:00
  → 扫描 status=待结算 且 eligibleAt ≤ now（跳过 arrivalHold=true 的到账冻结佣金）
  → 条件更新为「可提现」（影响行数 0 即跳过）
  → 若有欠款：deduct = min(debt, amount)，写 offsetToDebt，减 debt
  → 更新 promoterPending / promoterAvailable / promoterDebt
  → 站内信：已可随时申请提现
```

Apple 渠道佣金不参与上述日历解冻（`arrivalHold=true` 的记录被结算任务跳过）：
财务核对 Apple 结算报告与到账流水后，通过 `promote.appleSettle`（按支付月份）确认到账，
该月冻结佣金才解冻为「可提现」；解冻与日历结算同口径（抵扣欠款、站内信、留审计），重复确认幂等。

### 8.5 提现申请

```text
用户输入金额 gross（≥100，≤ available，≤20000）
  → 校验 eligible 佣金足够、无未完结提现（待审核 / 待打款 / 打款中）、当日 <3 次、欠款 ≤500
  → fee = round2(gross × 5%)
  → deductToDebt = min(debt, gross − fee)
  → net = gross − fee − deductToDebt（必须 > 0）
  → 原子写：activeKey=uid 唯一、requestId 唯一、promoterWithdrawing += gross
  → 状态「待审核」→ 通知用户
```

### 8.6 审核、待打款与人工执行

```text
财务审核（实名一致 / 无风险 / 协议有效）
  → 通过：条件更新「待审核 → 待打款」，记录审核人、payoutDeadlineAt = now + 24h
  → 生成出款明细：
       按 createdAt FIFO 选未核销佣金，覆盖 gross
       把 net 按毛额比例分配到各佣金（最大余数法补齐尾差）
       写 promotePayoutItems（status=todo，同一佣金仅一条 todo/doing）
  → 财务在「待打款」Tab 领取：
       条件更新「待打款 → 打款中」+ claimedBy；影响行数 0 说明已被他人领取
  → 导出 CSV → 商户平台手动操作：
       路径 A：对原订单发起分账（填接收方 openid 与金额）
       路径 B：发起商家转账到零钱
  → 财务回填：单据号 + 实际出款金额 + 出款时间 + 凭证 + 复核人（大额）
  → 系统校验：
       Σ 明细 = net − uncoveredAmount / 每笔明细 ≤ 佣金可用净额 / 单据号唯一 / 幂等 / 双人复核
  → 全部通过：「已到账」+ 核销佣金 + 更新汇总 + 通知
  → 校验不通过：拒绝落账，保持「打款中」，提示修正后重填
```

### 8.7 人工失败与退回余额

```text
路径 A 手动分账失败
  → 记录失败原因（不可分账 / 接收方异常 / 比例超限）
  → 改走路径 B（同一提现单继续），或人工「退回余额」

路径 B 手动转账失败
  → 修正信息后重新打款（回「打款中」）
  → 仍失败 → 人工「退回余额」

退回余额
  → 明细置 cancelled → 提现置「已撤销」→ 占用释放回 available
  → 佣金恢复可提现，用户可重新申请
  → 若本单存在已冲正佣金（`uncoveredAmount > 0`），只释放未被冲正的毛额，冲正部分不再释放
  → 未回填且超 24 小时：只标红提醒，不改变状态、不释放占用
```

口径：`promoterWithdrawn`（累计已提现）只累加真实出款明细的毛额；因退款冲正而失效的明细
（计入 `uncoveredAmount`）从未出款，不计入累计已提现，对账（4.8）按同一口径比对。

### 8.8 退款与分账回退

```text
用户申请退款 / 客服特批退款 / Apple 退款
  → 校验退款窗口与订单状态
  → 找该订单佣金
      ├─ 未出款：正常退款 → 冲正佣金（扣 pending / available）
      ├─ 已出款 · 路径 A 分账：财务先在商户平台按原单据号「分账回退」
      │     ├─ 回退成功：冲正时回填回退单号 → 原订单可退金额恢复 → 退款（冲正幂等跳过）
      │     └─ 回退失败：退款挂起、记欠款（净额）、中台告警；回退成功后再补录回退单号清欠款
      └─ 已出款 · 路径 B 转账：无法原路回退 → 冲正记欠款（净额）
            → 财务线下追回 / 推广者补足后补录凭证清欠款
  → 退款成功后写退款流水 → 更新佣金与汇总 → 通知

说明：
- 平台发起的退款（管理端退款 / 用户退款申请审核）在佣金已出款且未回填回退单号时会被拒绝，
  先由财务完成回退并回填，再发起退款。
- 微信 / Apple 渠道退款推送属于「退款已在支付渠道发生」，无法拦截：直接置退款成功，
  已出款未回退的佣金按 3.9 记欠款，待财务回退成功后补录回退单号清欠款。
```

## 附录 A · 术语

| 术语 | 含义 |
| --- | --- |
| 分账 | 微信支付把一笔订单资金拆给接收方；本期由财务在商户平台手动发起 |
| 分账接收方 | 分账的收款方，个人用 `PERSONAL_OPENID`，由财务在商户平台添加 |
| 分账回退 | 把已分出去的钱退回商户号，退款前必须做，本期手动发起 |
| 完结分账 | 商户平台手动解冻订单剩余未分账资金 |
| 商家转账 | 从商户号转到用户零钱，路径 B，由财务手动发起 |
| 待打款 | 审核已通过、等待财务执行的提现状态 |
| 打款中 | 财务已领取、正在商户平台操作的提现状态 |
| 回填 | 财务把单据号、金额、时间、凭证录回系统 |
| 出款明细 | `promotePayoutItems`，一笔佣金对应一条占用记录 |
| 计佣基数 | 实付扣通道成本后的金额 |
| 佣金毛额 / 净额 | 计提金额 / 扣 5% 手续费后实际出款金额 |
| 可提现日 | 支付次月 15 日 00:00 |

## 附录 B · 关键公式

```text
通道成本      C = round2(P × channelRate)
计佣基数      base = round2(P − C)
佣金毛额      G = round2(base × commissionRate)
手续费        F = round2(G × feeRate)
佣金净额      N = round2(G − F)
平台收入      P − N
平台实际留存  P − C − N

可提现日      eligibleAt = 次月 15 日 00:00（北京时间）
提现净额      net = round2(gross − fee − tax − deductToDebt) > 0
出款上限      payout ≤ round2(G × 95%) 且 ≤ round2(P × 30%)
```

## 附录 C · 判断口诀

```text
能分账走手动分账，不能分账走手动转账；
审核通过只放行，实际打款由财务执行；
回填校验过才算到账，未回填不核销；
手续费只降佣金，不算平台收入；
冻结到次月十五，之后随时可申请；
失败不释占用，人工退回才释放；
退款先退分账，回退不成转人工。
```
